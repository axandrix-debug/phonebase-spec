# Capability: performance

Операционализация «хорошая база данных» и «много записей» из ТЗ [[ТЗ]] [ADR-8].

## Requirements

### Requirement: Объём данных
Система SHALL штатно работать при 100 000 записей — рабочая интерпретация
«много записей» [[ТЗ]]. Контроль: память после загрузки ≤ 200 МБ
(tracemalloc, stdlib).

### Requirement: Бюджеты задержек
| Операция | Бюджет |
|---|---|
| Поиск в обе стороны | p99 ≤ 20 мс |
| Добавление записи | p95 ≤ 10 мс (ограничено fsync [[fsync]]) |
| Обновление / удаление | p95 ≤ 10 мс |
| Открытие БД со 100 000 записей | ≤ 3 с |
| Закрытие БД с компактификацией (100 000 записей) | ≤ 2 с |
| Действия GUI (поиск, открытие форм, добавление, удаление) | ≤ 200 мс |

Асимметрия перцентилей осознана: p99 для поиска (данные в памяти) и p95 для
записи — хвост fsync на потребительских SSD нестабилен [[fsync]].
Компактификация не выполняется внутри пользовательских операций
(`specs/storage/`) — её пик не попадает в строки выше.

### Requirement: Метрики надёжности
- Kill-тест (аварийные завершения в случайные моменты, ≥ 50 прогонов):
  0 потерянных подтверждённых операций; 0 частичных записей. Проверяет
  атомарность и учёт подтверждений; сверка после каждого прогона — через
  `count()`/`iter_all()` (`specs/api/`).
- Durability против потери питания — контракт fsync [[fsync]]; проверяется
  детерминированным corruption-fuzz: обрезка журнала на каждом байтовом
  смещении последней записи и порча случайных байтов — после каждого варианта
  reopen отдаёт все операции до точки повреждения.

### Requirement: Целевая конфигурация
Бюджеты — контракт для конфигурации: Windows 10+, NTFS, SSD (NVMe или SATA),
Python 3.12.x, машина без фоновой нагрузки. Benchmark-скрипт печатает
окружение (platform.platform(), stdlib). Первый шаг имплементации —
микробенчмарк fsync на целевой машине (10 000 × append+fsync, отчёт
p50/p95/p99): если p95 fsync > 7 мс, бюджет записи на этой машине недостижим
и пересматривается новым ADR (см. `specs/storage/tasks.md`).

### Requirement: Методика измерений
- ≥ 10 000 замеров на операцию; перцентили — nearest-rank.
- Первые 1 000 замеров каждой фазы (прогрев) отбрасываются.
- `gc.collect()` перед каждой фазой; фиксированный seed синтетики.
- Ошибочные операции (ValidationError / DuplicateError) из замеров исключаются
  — они измеряются юнит-тестами.
- Поиск по имени меряется на одно- и двухсимвольных префиксах (худший случай
  объёма выдачи при лимите 500) и на пустом префиксе (обзор).
- Fixture 100 000 записей создаётся bulk-путём (напрямую в журнал/снапшот) с
  проверкой `count() == 100 000` после открытия; время загрузки в бюджетах
  операций не участвует.
- GUI: инструментирование обработчиков (t0 на входе, t1 после отрисовки),
  прогон через `event_generate`, максимум по зафиксированному списку действий.

Критерии приёмки реализации: все тесты зелёные, бюджеты достигнуты на целевой
конфигурации.
