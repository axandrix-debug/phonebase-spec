# ADR — PhoneBase

Формат: Решение / Альтернативы / Мотивация / Последствия. Все статусы: accepted.
Источники расшифрованы в `openspec/project.md` (раздел «Источники»).

## ADR-1. Модель данных: плоская запись «Имя + Телефон»

**Решение.** Атомарная единица хранения — запись `(id, name, phone)`. Один
человек может иметь несколько записей (несколько телефонов); один телефон —
встречаться у нескольких записей (разные люди, домашний номер).

**Альтернативы.** Агрегат «Контакт» со списком телефонов; нормализованная
модель «имена ↔ телефоны» many-to-many.

**Мотивация.** ТЗ требует симметричный поиск в обе стороны [[ТЗ]]; плоская
модель даёт по одному простому индексу на каждое направление и простые
инварианты. Агрегат усложняет смену телефона и не добавляет ценности в рамках
ТЗ.

**Последствия.** Переименование человека с несколькими телефонами — это
несколько операций обновления. Для телефонной книжки сценарий редкий,
осознанно допускаем.

## ADR-2. Хранение: append-only журнал + снапшоты

**Решение.** Все операции дописываются в append-only журнал с fsync на каждой
операции; журнал — источник истины. Периодическая компактификация: снапшот
(атомарный rename) + обрезка журнала — для быстрого старта.

**Альтернативы.** Перезапись одного файла целиком; готовая СУБД — запрещено
ТЗ «с нуля» [[ТЗ]].

**Мотивация.** Дописывание в конец файла + fsync дают атомарность и
durability [[SQLite-atomic]]; перезапись всего файла — O(N) на каждую операцию
и риск потери при сбое посреди записи [[SQLite-atomic]].

**Последствия.** Добавление упирается в скорость fsync — бюджет 10 мс p95
достижим на SSD [[fsync]]; требуется механизм компактификации и восстановления.
Компактификация выполняется при открытии/закрытии БД, не внутри
пользовательских операций — пик задержки вынесен из интерактива (правка по
итогам ревью спеки).

## ADR-3. Канонизация телефонов и имён

**Решение.** Телефон хранится и сравнивается только в канонической форме
(правила — `specs/data-model/spec.md`: 11 цифр с ведущей «8» → «+7…»; ведущий
«+» сохраняется). Имя: отображаемая форма хранит регистр, ключ поиска —
casefold [[Python-casefold]].

**Альтернативы.** Хранить как введено и канонизировать при каждом поиске; не
канонизировать вообще.

**Мотивация.** Без канонизации поиск «+7 (921) 123-45-67» не найдёт
«89211234567» — прямое нарушение ТЗ «можно искать» [[ТЗ]]. Канонизация при
записи — одна точка истины, один набор правил.

**Последствия.** Исходное написание телефона не сохраняется. Для телефонной
книжки допустимо; при необходимости хранить «как введено» — новый ADR.
Допущение о российском плане нумерации подтверждено владельцем продукта
(2026-10-28): правило «8→+7» сохраняется, 10-значные номера унифицируются
с формой «+7…» — см. ADR-10.

## ADR-4. GUI: Tkinter, только стандартная библиотека

**Решение.** GUI — Tkinter; весь проект — только Python stdlib.

**Альтернативы.** Web-UI (Flask/FastAPI + браузер); PyQt; TUI.

**Мотивация.** «С нуля» трактуем как минимум внешних зависимостей; Tkinter
входит в стандартную библиотеку [[Python-tkinter]] и покрывает потребности
(таблица, формы, диалоги). Web-UI тянет сервер и многопользовательность —
вне рамок ТЗ.

**Последствия.** Внешний вид скромный; ТЗ требует «визуальный UI», а не
«красивый UI» [[ТЗ]].

## ADR-5. Однопользовательская, однопроцессная система

**Решение.** Без сети и конкурентного доступа. Второй экземпляр на той же
директории БД блокируется lock-файлом (DatabaseLockedError).

**Альтернативы.** Клиент-сервер; многопоточный доступ с блокировками.

**Мотивация.** ТЗ не требует многопользовательности [[ТЗ]]; сужение контекста
резко упрощает ядро и его доказуемую корректность.

**Последствия.** Сетевой API — кандидат в v2; контракт библиотеки спроектирован
так, чтобы серверный слой добавился поверх без смены ядра.

## ADR-6. Запрет дубликатов пары (name_key, phone)

**Решение.** Пара (ключ имени, канонический телефон) уникальна в пределах БД;
попытка дубликата → DuplicateError.

**Альтернативы.** Разрешать дубликаты; молча мержить при добавлении.

**Мотивация.** Дубликаты засоряют выдачу поиска и делают обновления
непредсказуемыми; уникальность соответствует интуиции «хорошей БД» [[ТЗ]].

**Последствия.** Кейс «два человека — один домашний номер» остаётся возможен
(имена разные); запрещена только полностью идентичная пара.

## ADR-7. Только точный поиск (superseded)

> Статус: заменён решением ADR-9 (префиксный поиск по имени) по решению
> владельца продукта, 2026-10-28. Текст сохранён для истории.

**Решение.** Поиск — точное совпадение канонических форм. Подстрока, префикс,
нечёткость — вне рамок v1.

**Альтернативы.** Префиксный поиск (индекс-trie); fuzzy-поиск.

**Мотивация.** ТЗ формулирует поиск как соответствие «имя ↔ телефон» [[ТЗ]];
расширения требуют других структур данных и не запрошены.

**Последствия.** Запрос «Иван» не найдёт «Ивана Петрова» — осознанное
ограничение; зафиксировано в README (CUJ-3) для проверки владельцем продукта.

## ADR-8. Операционализация «хорошая» и «много»

**Решение.** «Много записей» = 100 000; «надёжно» = durability-гарантии
(D1–D3 в `specs/storage/`) и crash-тест; «хорошая» = измеримые бюджеты
задержек (`specs/performance/`).

**Альтернативы.** Оставить качественные формулировки («быстро», «надёжно»).

**Мотивация.** Нефункциональное требование без числа неверифицируемо; урок
требует Proof — theoretical vs practical [[Урок]] стр. 45, пример урока —
«менее 20 мс в 99% случаев».

**Последствия.** Цифры становятся контрактами приёмки; их пересмотр — только
через новый ADR.

## ADR-9. Префиксный поиск по имени

**Решение.** Поиск по имени — префиксное совпадение по name_key: запрос
«Иван» находит «Ивана Петрова». Поиск по телефону остаётся точным. Решение
владельца продукта, подтверждено 2026-10-28 при утверждении CUJ; заменяет
ADR-7.

**Альтернативы.** Точный поиск (ADR-7, superseded) — воспринимается
пользователем как «сломанный поиск» (находка ревью спеки); подстрока —
полный скан 100 000 записей ставит бюджет p99 ≤ 20 мс под риск.

**Мотивация.** CUJ-3: оператор помнит начало имени, а не полное.
Отсортированный по name_key индекс (trie или сортированный список с
бинарным поиском) даёт префиксный поиск за O(log n + выдача) — бюджеты
производительности не меняются.

**Последствия.** Пустой префикс означает «с начала базы» — на этом основан
обзор книжки (CUJ-5): выдача ограничена лимитом (по умолчанию 500).

## ADR-10. 10-значные номера унифицируются с формой «+7…»

**Решение.** Каноническая форма 10-значного номера без ведущего «+» —
«+7» + все 10 цифр: «9211234567» = «+79211234567» = «89211234567». Короткие
номера (3–6 цифр) не преобразуются. Решение владельца продукта,
подтверждено 2026-10-28.

**Альтернативы.** Оставить как есть (ограничение, зафиксированное ревью) —
один реальный номер в двух форматах давал бы две записи с промахом поиска;
преобразовывать только номера с первой «9» — городские 10-значные («812…»)
остались бы неунифицированными.

**Мотивация.** В российской телефонии 10-значный номер — полный национальный
формат (код города/оператора + номер); унификация закрывает промах поиска
из CUJ-1/CUJ-3 для самого частого формата ручного ввода.

**Последствия.** Не-российский 10-значный номер без «+» получит «+7» —
принятое следствие российского контекста продукта; номера с ведущим «+»
не затрагиваются.
